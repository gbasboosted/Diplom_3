# Stellar Burgers UI

Задание 3: UI-тесты на Selenium, pytest и Allure в Chrome и Firefox.

Целевой стенд: https://qa-stellarburgers.education-services.ru/.

## Сценарии

| Функциональность | Проверка |
| --- | --- |
| Конструктор | Переход по ссылке в шапке из ленты заказов |
| Лента заказов | Переход по ссылке в шапке из конструктора |
| Детали ингредиента | Открытие окна и соответствие названия выбранному ингредиенту |
| Закрытие окна | Закрытие крестиком и возвращение в конструктор |
| Добавление ингредиента | Увеличение счётчика начинки на единицу после перетаскивания |
| Выполнено за всё время | Увеличение счётчика после оформления собственного заказа |
| Выполнено за сегодня | Увеличение счётчика после оформления собственного заказа |
| В работе | Появление номера оформленного заказа в соответствующем списке |

Каждый из восьми сценариев параметризован для **Google Chrome и Mozilla Firefox**:
всего **16 запусков**. Каждый тест получает новый браузер и отдельный профиль.

## Установка и запуск

Нужны Python 3.10+, установленные Google Chrome и Mozilla Firefox и доступ к стенду:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest
```

В Windows активация: `.venv\Scripts\activate`. По умолчанию браузеры работают
в headless-режиме с размером окна 1440×1000. Selenium Manager подбирает драйверы;
при первом запуске ему может понадобиться доступ к серверам производителей.

Выбор браузера и запуск с видимым окном:

```bash
python -m pytest --browser chrome
python -m pytest --browser firefox
python -m pytest --browser chrome --browser firefox --headed
```

## Page Object

Локаторы вынесены в `locators/`; с драйвером и DOM взаимодействует только `BasePage`.
Остальные страницы и тесты вызывают его методы. Используются явные ожидания
`WebDriverWait`, без `time.sleep` и неявных ожиданий.

- `BasePage`: открытие страниц, поиск и ввод, ожидания, перетаскивание,
  скрипты наблюдения за DOM, переключение вкладок и диагностика при ошибке.
- `ConstructorPage`: карточки, перетаскивание ингредиентов, счётчики и оформление заказа.
- `Modal`: детали ингредиента, крестик, подтверждение и номер заказа.
- `LoginPage`: вход через форму.
- `FeedPage`: счётчики, карточки заказов и список «В работе».

Каждый метод страниц, включая базовый класс и конструктор, имеет декоратор
`@allure.step`. Объекты страниц и модальных окон создаются только в тестах
или фикстурах: страницы не создают друг друга. Нажатие кнопки оформления заказа
и чтение его номера из модального окна — отдельные действия соответствующих объектов.

Для заказов фикстура регистрирует уникального пользователя через API, затем
`LoginPage` выполняет вход через UI. Сборка бургера и оформление заказа происходят
через UI. Созданный пользователь удаляется через API в teardown даже при падении
теста. Генерация данных вынесена в `helpers.make_user`; фикстура её только вызывает.
Пароль представлен `SecretText`, исключён из `repr` данных пользователя
и не раскрывается при записи параметров декораторов Allure.
Ошибки удаления не скрываются. Метода удаления заказов в документации нет,
поэтому созданные заказы остаются на учебном стенде.

В Chrome используется нативное перетаскивание Selenium `ActionChains` с удержанием,
начальным сдвигом мыши для запуска `dragstart` и отпусканием над корзиной.
Перед переносом выполняется мгновенная прокрутка, без ожидания плавной анимации.
В Firefox используются DOM-события HTML5 `DragEvent` с общим `DataTransfer`:
Gecko не запускает перетаскивание этого приложения через pointer actions.
События обрабатывает само приложение; React/Redux и ответы API не подменяются.
Результат проверяется по реальному счётчику в DOM. Перед кликами и добавлением
ингредиентов тест ждёт исчезновения загрузочных подложек.

Перед заказом лента открывается во второй вкладке. Счётчик сравнивается со значением
до оформления, а появление **собственного номера заказа** в ленте проверяется
отдельно. Ожидается увеличение, а не строго `+1`: на общем стенде одновременно
могут создавать заказы другие пользователи.

Для «В работе» до отправки заказа включается `MutationObserver`, который запоминает
номера, реально появлявшиеся в этом разделе DOM. Это позволяет проверить появление
номера, даже если заказ успел перейти в следующий статус, пока вкладка конструктора
ожидала подтверждение. Наблюдатель только читает DOM, данные приложения не меняются.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `STELLAR_BURGERS_URL` | `https://qa-stellarburgers.education-services.ru` | Целевой стенд |
| `PAGE_LOAD_TIMEOUT` | `30` | Таймаут загрузки страницы, секунды |
| `UI_WAIT_TIMEOUT` | `20` | Ожидание элементов и изменений DOM |
| `API_TIMEOUT` | `20` | Запросы подготовки и очистки пользователя |
| `ORDER_TIMEOUT` | `60` | Ожидание подтверждения заказа |
| `CHROMEDRIVER_PATH`, `GECKODRIVER_PATH` | Не заданы | Явный путь к драйверу вместо Selenium Manager |
| `CHROME_BINARY`, `FIREFOX_BINARY` | Не заданы | Явный путь к браузеру |

Например, ограниченный по времени диагностический прогон:

```bash
PAGE_LOAD_TIMEOUT=5 UI_WAIT_TIMEOUT=5 API_TIMEOUT=5 python -m pytest --tb=short
```

## Allure

Результаты сохраняются в `allure-results/`, HTML-отчёт — в
`reports/allure/index.html`. При каждом запуске pytest каталог результатов
очищается. В отчёте есть шаги, параметры браузера и его фактическая версия.
При ошибке прикладываются снимок экрана, копия DOM без значений полей и URL.
Пароли и токены не передаются в названия шагов и не прикладываются к отчёту.

Для генерации одного автономного HTML-файла нужен Node.js 22+ и pnpm 11.25.0:

```bash
pnpm install --frozen-lockfile
pnpm run report
```

HTML можно открыть прямо из файловой системы, Java не требуется. При наличии
Allure 2 CLI те же сырые результаты можно просмотреть обычным способом:

```bash
allure serve allure-results
```

### Сохранённый прогон и CI

После исправления замечаний ревьюера выполнена команда
`python -m pytest --browser chrome --browser firefox --tb=short`
на https://qa-stellarburgers.education-services.ru/.
Результат: **16 passed** — по 8 проверок в Chrome 156.0.8078.48
и Firefox 158.0.1. Пройдены все сценарии: навигация, открытие и закрытие
деталей, добавление начинки, оба счётчика ленты и появление своего номера «В работе».
Подготовка и удаление пользователей прошли без ошибок. В `allure-results/`
и HTML-отчёте сохранён именно этот полный прогон, без результатов промежуточных запусков.

Workflow запускает оба браузера при изменениях кода в `develop3`, при pull request
в `main` и вручную. Результаты и отчёт сохраняются даже при ошибках тестов,
срок хранения CI-артефакта — 30 дней. Изменения только README и отчётов не запускают CI.

## Локаторы QA-стенда

Локаторы проверены по фактическому DOM QA-стенда. Учтены путь `/ingredient/`,
подпись ссылки «Лента Заказов», поле email `input[type='text']` и классы карточек.
Булочка «Краторная булка N-200i» и начинка «Мясо бессмертных моллюсков Protostomia»
находятся по `alt` изображения в карточке. Крестик определяется по типу кнопки
и смысловой части её CSS-класса. Позиционные индексы для них не используются;
хеши CSS-модулей и ID ингредиентов в локаторах не зафиксированы.
Закрытие окна проверяет его исчезновение, без лишнего требования сменить URL.
Ожидание номера заказа исключает временное значение `9999`, которое видно
в разметке приложения до ответа сервера.
